# 08 — Security

## 1. Authentication

- **Staff/product users**: Supabase Auth (email/password + OAuth providers as configured), session JWTs short-lived with refresh rotation. Email confirmation is required before a session is usable — `create_organization_with_owner()` grants `org_admin` at signup time, so an unconfirmed address must never be enough to act with that role (M1.3, config-as-code in `packages/database/supabase/config.toml`'s `[auth.email]`). Password policy: minimum 8 characters, must include lower+upper+digit (`minimum_password_length`/`password_requirements` in the same file) — a deliberate, reviewed value, not the CLI's weaker default. MFA (TOTP) available at the organization level, required for `agency_owner`/`agency_admin` roles once available (Phase 8 enterprise hardening; not an MVP blocker per the SOC2 deferral).
- **Portal users**: separate magic-link authentication flow, issuing a JWT scoped exclusively to portal permissions — structurally unable to authenticate into the internal product, not merely permission-gated (`04-API-Architecture.md` §3).
- **API keys**: hashed at rest (never stored or logged in plaintext), prefixed by environment (`arev_live_`/`arev_test_`) for operator clarity, individually revocable, scoped to one organization and an explicit permission subset.
- **Service-to-service (n8n → API)**: n8n uses the same `api_keys` mechanism as any external integrator, scoped to a `service` role and issued per workflow (`04-API-Architecture.md` §3) — one credential primitive across every caller type, not a separate, undocumented mechanism.
- **Brute-force protection**: login attempts are rate-limited per account and per source IP, with progressive backoff and an account-lockout threshold after repeated failures — a standard control that applies independently of the API-level rate limiting in `04-API-Architecture.md` §6, which governs authenticated request volume, not login attempts themselves.

### 1.1 Milestone 3.3 implementation scope — API-key request authentication, now real

The "service-to-service (n8n → API)" bullet above described the *intended* model since M1.7; the table existed but nothing validated a presented key until now. As of Milestone 3.3:

- `resolve_api_key(p_key_hash text)` (`SECURITY DEFINER`, `03-Database-Architecture.md` §2.1) resolves a pre-hashed Bearer token to `(api_key_id, organization_id, scopes)` in one atomic `UPDATE ... RETURNING`, bumping `last_used_at`. No `auth.uid()` guard, by design — mirrors `resolve_tracking_site()`'s own established precedent exactly: a machine credential has no session identity to check against, its authorization primitive is possession of the correctly-hashed key. Returns zero rows, never a distinguishable error, for a nonexistent, revoked, or hash-mismatched key — the same non-oracle doctrine this schema already applies to every other credential-resolution function.
- `organization_id` is taken **exclusively** from the matched `api_keys` row — never a caller-supplied field of any kind, closing the same class of tenant-spoofing risk §2 below describes for every other caller type.
- `packages/auth`'s `resolveServiceActorFromApiKey`/`ServiceActor`/`hasScope` is a deliberately **separate** resolver from `resolveRequestContext()` (session auth) — a `ServiceActor` is not an `Actor`, has no `RoleKey`, and is never checked via `can()`/`PERMISSION_MATRIX`. Authorization is scope-based, reading `api_keys.scopes` (a jsonb column that existed, unused, since M1.7) — a deliberately narrower, separate mechanism from RBAC, appropriate for a machine credential rather than a human staff role.
- A route must explicitly call `resolveScopedServiceActor(request, requiredScope)` to accept API-key auth — nothing makes it happen implicitly. As of this milestone, exactly two routes do (`04-API-Architecture.md` §2.8, the enrichment write-back endpoints, `enrichment:write` scope) — confirmed by direct search that no existing session-authenticated staff route was changed or accidentally became API-key-accessible.
- Hostile-tested directly against real Postgres across four sequential Final Implementation Acceptance Audits (`docs/13-Technical-Design-Review.md` "Milestone 3.3 — Overall Closeout"): a revoked key resolves to zero rows; a tampered/nonexistent hash resolves to zero rows, indistinguishable from revoked; a cross-tenant write attempt (a correctly-scoped key, an entity UUID belonging to a different organization) is independently rejected twice over — by a composite tenant-safe foreign key at the database layer *and* by RLS `WITH CHECK`, neither relying on the other.

## 2. Authorization

Three pillars, not two:

- **RBAC** (§3) and **Postgres RLS** as defense-in-depth beneath the application-layer `can(actor, action, resource)` facade (`02-Software-Architecture.md` §7, `03-Database-Architecture.md` §5) — neither layer alone is trusted as sufficient; a bug in one is caught by the other.
- **Tenant context resolution**: `organization_id` is never accepted as a client-supplied parameter. Concretely, every request — JWT session, API key, or n8n service credential alike — resolves to an authorized organization via a single request-scoped Postgres session setting, populated once by API middleware at the start of each request (`03-Database-Architecture.md` §5). This is what prevents tenant-spoofing, and it's also what makes an agency user's context switch between client organizations take effect immediately, rather than waiting on a stale JWT claim.
- **RLS policies require base table grants to actually take effect**: a table with RLS enabled but no `GRANT` for the `authenticated`/`anon` roles fails closed with a permission error rather than an RLS denial — verified during M1.2's isolation testing, not assumed (ADR-003). Both layers — grant and policy — are required together; neither alone is the enforcement mechanism.
- **RLS does not filter every privilege — `TRUNCATE` is a real gap, not a theoretical one**: discovered during M1.7's mandated security review (a platform-wide gap present since M1.2, not introduced by M1.7). The Supabase CLI's local bootstrap applies a default ACL granting `TRUNCATE`/`REFERENCES`/`TRIGGER` on every new table to `authenticated`/`anon` — and Postgres RLS does not govern `TRUNCATE` at all, so a role holding it can wipe an entire tenant-scoped table with zero per-row scoping possible, regardless of any RLS policy protecting `SELECT`/`INSERT`/`UPDATE`/`DELETE` on that same table. Verified empirically, not assumed: `authenticated` could genuinely execute `TRUNCATE public.consent_records` before the fix. Closed by `packages/database/supabase/migrations/20260811100000_revoke_dangerous_default_table_privileges.sql`, which both revokes the existing grants and corrects the default ACL so tables created by future migrations don't reacquire them — regression-tested (`table-privilege-hardening.test.ts`) so this specific gap cannot silently reopen. Worth stating as a standing rule: **every migration that creates a table must be reviewed for what it grants beyond what it explicitly asked for, not only for what it explicitly granted** — a lesson RLS-policy review alone would never have caught, since RLS was never the layer at fault here.
- **RLS is not a substitute for least-privilege grants — a `security_invoker = false` view can let `INSERT` bypass RLS entirely, even with `TRUNCATE`/`REFERENCES`/`TRIGGER` already closed**: found during the default-ACL hardening review that followed the fix above, once the same Cloud default-ACL bootstrap was inspected for `SELECT`/`INSERT`/`UPDATE`/`DELETE`, not just `TRUNCATE`. Cloud's default ACL grants full CRUD on every table (and view) to **both** `anon` and `authenticated`. `agency_rollup_organizations` is deliberately `security_invoker = false` (`03-Database-Architecture.md` §5) so its own `WHERE` clause can bypass `organizations`' single-org `SELECT` policy for the legitimate agency roll-up read — but a view's `WHERE` clause only ever filters `SELECT`/`UPDATE`/`DELETE`, **never `INSERT`**, and the view runs as its *owner* for permission purposes, not the caller. The result: any role holding an `INSERT` grant on the view — which the default ACL gave to both `anon` and `authenticated` — could insert an arbitrary row directly into `organizations`, completely bypassing that table's own `INSERT` policy. Verified empirically: committed a real proof-of-concept row as an unauthenticated `anon` session (with zero legitimate agency context), confirmed it existed in the base table, then deleted it; reproduced identically for an `authenticated` caller with no agency membership at all. Closed by `packages/database/supabase/migrations/20260811110000_harden_default_table_privileges.sql` — regression-tested (`default-acl-hardening.test.ts`). **The standing rule this adds, distinct from the `TRUNCATE` lesson above**: a `security_invoker = false` view is not merely "RLS bypassed for reads by design" — it is *RLS bypassed for every operation the view's grants permit*, including ones (`INSERT`) the view's own defining query was never written to restrict. Any future `security_invoker = false` view must be granted only the exact operations it is actually meant to support (this one: `SELECT` only), never inherit a blanket default.
- **Agent approval gating**: a third, AI-specific authorization pillar alongside RBAC and RLS. Tools an AI agent can call are tagged `requires_human_approval: true/false` (`05-AI-Agent-Architecture.md` §1); for `true` tools (a proposed deal-stage change, a proposed meeting time, sending an email), the tool call never commits the underlying write directly — it produces a proposal object that only a separate, human-only action can confirm. This is enforced at the tool-execution layer, not by prompting the model to ask first, and it exists specifically so an agent's standing permission grant (RBAC) is never sufficient on its own to take a consequential action without a human in the loop.
- Agency cross-org access is implemented only through explicit, named `agency_rollup_*` views — never a generic bypass flag checked ad hoc in application code (`03-Database-Architecture.md` §5).

### 2.1 Lead Scoring — deterministic rule evaluation only, no eval/agent involvement (Milestone 3.4)

Organization-owned `scoring_rules` are attacker-controllable configuration in the threat-modeling sense (any `org_admin` can author one) — the containment guarantee is that a rule can never become executable code, only allowlisted data. A rule's `field` (11-value fixed set), `operator` (9-value fixed set), and `value` (shape derived from the field's own declared type) are validated against a closed allowlist at write time (`scoring-rule-validation.ts`, backed by a coarse `CHECK` constraint at the database layer as defense-in-depth, never the primary gate); by the time `computeScore` (`packages/intelligence/src/scoring.ts`) reads a rule, `field` is a string that already passed that allowlist, safe by construction, not by a runtime check performed inside the evaluator itself. `computeScore` is a fixed, hand-written TypeScript interpreter over a plain fact object — **no `eval`, no `new Function`, no dynamic SQL construction from rule content, and no LLM/agent involvement anywhere in this module**, for any rule, under any organization, ever. This was verified hostilely, not merely designed: submitting `field: "__proto__"` (and other `Object.prototype` member names, exploiting JavaScript's own `in`-operator prototype-chain lookup) was found during this milestone's own acceptance-audit remediation to bypass an earlier, incorrect allowlist check and crash the request handler — fixed with an own-property check, reproduced clean post-fix on both `POST` and `PATCH`, zero rows ever written either way. No AI/ML/agent-assisted scoring exists or is planned as part of this milestone — an explicit accepted-design exclusion (`02-Software-Architecture.md` §7), not a temporary limitation; any future agent-adjusted scoring (`05-AI-Agent-Architecture.md`'s own Scoring Agent persona, Phase 4) is a separate, later, explicitly out-of-scope feature.

- Permission checks are resource + action pairs (`contacts:read`, `contacts:create`, `contacts:update`, `contacts:delete`, `deals:write`, `proposals:send`, `agents:trigger`, `settings:billing`), not coarse role checks scattered through the codebase — the RBAC facade (`can(actor, action, resource)`) is the single place this matrix is evaluated. - AI agents carry no standing permission beyond what the triggering user/organization context already grants — a tool call an agent makes is checked identically to the equivalent human action (`05-AI-Agent-Architecture.md` §1), **and consequential tools additionally require the human-approval gate described in §2** — RBAC scoping and approval gating are independent controls, both required where applicable, not substitutes for each other.
- API keys carry their own scoped permission subset independent of the issuing user's role, so a key can be handed to a third party without over-granting.

Agency roll-up access to Deals/Pipelines remains explicitly out of scope for this milestone.

The full matrix lives in `packages/auth/src/permissions.ts` — this table mirrors it for the scope actually built so far and must be kept in sync as new permissions are added there.

## 4. Encryption

- **In transit**: TLS everywhere (Vercel, Supabase, n8n instance, all provider calls) — no unencrypted internal traffic, including app-to-n8n webhook calls.
- **At rest**: Supabase-managed encryption at the storage layer for the full database and Storage buckets, plus **column-level encryption** (pgsodium/pgcrypto) for the highest-sensitivity fields specifically: `integration_connections.credentials_encrypted`, `api_keys.key_hash`, any stored OAuth tokens, and — with the AI Revenue Brain — `meetings.transcript_text`/`recording_url` and `email_messages.body_text`, given these are raw correspondence/recording content rather than structured CRM fields. These remain encrypted even from a database dump or a compromised read-replica — not just relying on disk-level encryption.
- **Secrets management**: all provider API keys, signing secrets, and service credentials live in Vercel/Supabase environment secret stores — never committed to the repository, never present in client-side bundles, never logged in plaintext (structured logging redacts known secret-shaped fields).
- **Key rotation**: encryption keys and provider credentials are rotatable without a schema change or downtime — `integration_connections` supports re-encryption in place, keyed by a versioned key reference.

### 4.1 Visitor Identification — Ed25519 Trust Model (Milestone 3.2)

**Architecture amendment**: the Milestone 3.2 design originally accepted an HMAC/shared-secret model, assuming a reusable encrypted-secret-storage primitive (mirroring `integration_connections.credentials_encrypted`, §4 above) that could hold a signing secret. Before any code was written, the Milestone 3.2 Phase-0 feasibility check confirmed **empirically, not theoretically**, that no such primitive actually existed anywhere in this repository — `integration_connections` itself was unbuilt. Continuing with HMAC would have required inventing a new master-key/reversible-secret architecture with no established precedent, which was rejected outright rather than worked around. The design was amended instead: **Ed25519 asymmetric signing**, which removes the reversible-secret requirement by construction, since a public key is not a secret at all.

**Trust boundary**:
- The customer's own trusted backend is the sole authority that establishes a visitor's identity. It generates and permanently retains the Ed25519 private key.
- This platform never receives, generates, stores, logs, or transmits the private key — only the corresponding public key (`tracking_site_public_keys.public_key_pem`, SPKI PEM), which requires no encryption at rest, since it is not confidential.
- The browser is a pure relay: `aiRevenueOsTracker.identify(assertion)` (Milestone 3.2E) accepts a short-lived signed assertion the host page obtained from the customer's own backend out of band, and forwards it to `POST /track/identify` unparsed, unverified, and unpersisted — the tracker never has any cryptographic capability of its own.
- This platform verifies every assertion server-side before acting on it (`packages/auth`'s `tracking-identity-assertions`/`tracking-signing-keys`, `docs/04-API-Architecture.md` §2.7).

**Assertion format**: `base64url(claimsJson) + "." + base64url(signature)` — deliberately not JWT/JWS-compatible. A general JWT library, or a hand-rolled JWS-compatible parser, was considered and rejected: JWS's own negotiable `alg` header is exactly the surface algorithm-confusion attacks exploit, and reproducing that surface for a single-purpose, single-algorithm assertion would be unnecessary protocol risk for no real benefit. This format has no header segment and no algorithm field at all — the verifier applies Ed25519 unconditionally; there is nothing in the token capable of selecting a different algorithm.

**Claims and verification, in order**:
1. **Structural parse** — exactly one `.` separator, both segments valid base64url, a 64-byte signature, bounded total length (2048 chars) — rejected before any decoding or crypto work.
2. **Claims shape** — `iss` (must equal the fixed issuer string `"ai-revenue-os:visitor-identify"`), `aud` (must equal the resolved `trackingSiteId` — binds the assertion to one specific tracking site), `kid` (selects which registered public key verifies this assertion), `email` (the sole contact-resolution evidence carried in the token — never a raw `contactId`), `iat`/`exp`, `jti` (single-use replay-protection nonce), and two **optional** defense-in-depth bindings: `organizationId` (redundant cross-check against the resolved tracking site's own organization) and `anonymousId` (binds the assertion to one specific browser/visitor session when present).
3. **Freshness** — lifetime is capped at 300 seconds server-side regardless of whatever `iat`/`exp` the customer's backend actually signs (closes off an artificially long-lived token), with a 30-second clock-skew tolerance between the customer's backend and this platform.
4. **Key resolution** — `kid` is looked up scoped to `(organizationId, trackingSiteId, kid)` together, never by `kid` alone, and only a currently non-revoked key resolves — so a `kid` can never select a key belonging to a different tenant or a different tracking site, and a revoked key's assertions are unconditionally rejected, regardless of what an attacker-controlled token claims.
5. **Signature verification** — re-checks the resolved key's `asymmetricKeyType === "ed25519"` independently immediately before verifying (defense in depth against algorithm confusion even in the hypothetical case a non-Ed25519 key somehow reached this step), then verifies the signature over the exact UTF-8 bytes of the transmitted claims segment.

Any failure at any step is treated identically — verification returns `null`, never a distinguishable reason, preserving `POST /track/identify`'s non-oracle response design (`docs/04-API-Architecture.md` §2.7).

**Replay protection**: `jti` is consumed exactly once via `visitor_identifications`' tenant-scoped `UNIQUE (organization_id, token_jti)` constraint — structural, not an application-trusted check. A replayed `jti` is rejected identically whether it lands on the normal identification path or an identity-conflict rejection path (Milestone 3.2 acceptance-audit remediation — the conflict-rejection path originally let a unique-constraint violation escape as an uncaught exception; both paths now resolve to the same non-throwing rejection).

**Runtime privacy guarantees**: identification additionally requires a live, currently-granted `cookie_tracking` consent, re-checked inside the same atomic transaction as the write — an assertion signed minutes ago against a since-withdrawn consent is rejected regardless of its own validity. No raw assertion string, decoded claims, or email is ever persisted or logged anywhere in the identification path — `visitor_identifications` stores only organization-scoped identifiers and a closed `event_type` vocabulary (`docs/03-Database-Architecture.md` §2.3).

## 5. GDPR

- **Consent management**: `consent_records` is append-only (a withdrawal is a new row, never an update to the prior grant), covering `marketing_email`, `cookie_tracking`, `data_processing`, and — as of the AI Revenue Brain (`11-AI-Revenue-Brain.md`) — `email_content_processing` and `meeting_recording_processing` as distinct, stricter consent types, all tracked independently. A contact can withdraw marketing consent while data processing for CRM purposes continues under legitimate interest, or withdraw email/meeting content processing specifically while still being a normal CRM contact — the Brain's ingestion workflows (`06-n8n-Workflow-Architecture.md` §10-13) hard-gate on these per-source consent types, not a single blanket flag.
- **Data Subject Access/Export/Deletion Requests — hard deletion, never the ordinary soft-delete**: `data_subject_requests` drives an orchestrated job that cascades across every domain holding personal data — CRM (contacts, activities, notes), Intelligence (visitor records, enrichment, scores) — with a 30-day SLA timer and audit trail of completion. **This is categorically distinct from the `deleted_at` soft-delete used for ordinary, recoverable, user-initiated deletion elsewhere in the platform** (`03-Database-Architecture.md`'s deletion model): a completed deletion request always performs actual hard deletion of the row, or irreversible anonymization of personal-data columns where the row must survive for referential/audit reasons. A `deleted_at` timestamp on a contact does not, by itself, satisfy an erasure obligation — the data is still physically present. **The AI Revenue Brain extends this cascade**, since it is designed to be the platform's single largest aggregation of personal data — as of Milestone 4.1 Phase 1 this covers `brain_entity_profiles`/`brain_entity_profile_history`/`brain_embedding_entity_refs` (structural FK cascade) and `brain_embeddings` (targeted-capture full-artifact deletion, see §5.2 below); AI agent memory/chat/conversation-thread tables and `email_messages`/`meetings` remain future scope, since none of those tables exist yet (`03-Database-Architecture.md` §2.4, §2.9). This cascade is a Phase 1 primitive (`09-Development-Roadmap.md`) extended piece by piece as each part of the Brain ships — not a script retrofitted onto live data later.
- **Data minimization**: enrichment and visitor-tracking data is stored only as long as `data_retention_policies` specifies per data type; the Support/Chat Agent explicitly avoids persisting cross-session memory of portal customer queries beyond support continuity needs (`05-AI-Agent-Architecture.md` §6). Meeting transcripts/recordings — likely the most sensitive artifact in the entire platform — get the shortest justified retention period of any data type, reviewed explicitly rather than defaulting to the platform's general retention window.
- **Public website tracking (Milestone 3.1) — durable security/privacy guarantees**: server-side consent remains authoritative for every tracking event — `POST /track/collect` re-checks `cookie_tracking` consent inside the same atomic transaction as the write itself, on every single call, never trusting the browser's own local consent state; an event cannot persist without a currently-granted consent row. `organizationId` is never accepted as a client-supplied field on any public tracking endpoint — it is always resolved server-side from the tracking site key. The site key (`tracking_sites.id`) is intentionally public and non-secret (`03-Database-Architecture.md`); it functions purely as routing context for resolving an `organization_id`, never as an authorization credential — possessing it grants no elevated database privilege, since every tracking write still runs through the same `authenticated`-role connection every other request uses, never `service_role`. Rate-limit buckets never store a raw `anonymous_id`/IP/site key, only an opaque SHA-256 hash; a source IP that doesn't parse as a genuine IPv4/IPv6 address (validated via Node's built-in `isIP()`) collapses to a fixed `"unknown"` bucket rather than becoming its own distinct identifier. Public tracking responses deliberately preserve non-oracle behavior — a persisted event, a missing consent grant, a revoked tracking site, and a nonexistent site key all produce an identical response, so no caller can distinguish tenant state by probing. The official browser tracking script (Milestone 3.1D) never inspects DOM/form values automatically (only an explicit, caller-invoked `track()` call can send `click`/`form_submit` data, and even then only caller-supplied `metadata` — never scraped page content), and never transmits a full URL, query string, or fragment — `url`/`referrer`/`landingPage` are reduced to `origin + pathname` before leaving the browser.
- **Visitor identification (Milestone 3.2) — consent, withdrawal, and erasure guarantees**: identification via `POST /track/identify` requires a live, currently-granted `cookie_tracking` consent re-checked inside the same atomic transaction as the identity write, exactly like collection — a signed assertion that is otherwise perfectly valid is still rejected without a current consent grant. **Withdrawal atomically unlinks**: when a visitor's consent status changes to `withdrawn` (`POST /track/consent`), the same transaction that records the withdrawal also clears `website_visitors.identified_contact_id` (`unlinkVisitorIdentityOnWithdrawal`, `packages/intelligence`) — an identified visitor never remains identified past the moment consent is withdrawn. This unlink is reversible in principle (a later re-grant plus a fresh identification is allowed) and deliberately does not set `identification_suppressed_at` — permanent suppression is reserved for erasure alone. **Erasure permanently prevents re-identification**: `execute_contact_erasure()` (`docs/03-Database-Architecture.md` §2.8), extended in Milestone 3.2F, sets `identification_suppressed_at` on every `website_visitors` row currently identified to the contact being hard-erased, before the contact row itself is deleted — a permanently non-null value that makes that specific visitor row ineligible for identification to any contact, ever again, closing the gap where the browser's continued possession of the same `anonymous_id` could otherwise silently re-associate a hard-erased person's retained anonymous history with a replacement or newly-created contact. No signed assertion, decoded claims, raw evidence, or email is ever persisted or logged anywhere in the identification path — see §4.1 for the full Ed25519 trust model.
- **Lead scoring (Milestone 3.4) — erasure cascade and consent-withdrawal attribution**: `lead_scores` has a composite tenant-safe FK to `contacts` with `ON DELETE CASCADE` — a hard-erased contact's entire score history is removed as part of the same erasure, verified end-to-end via the real `execute_contact_erasure()` path (not a raw `DELETE`); a contact later recreated under the same email gets a genuinely new id with zero inherited score history, and a stale trigger referencing the erased contact's old id is cleanly rejected (`contact_not_found`), never reattached to the new identity. Historical score rows remain historical until erasure — withdrawal alone does not retroactively rewrite them. **New calculations respect current attribution**: after a visitor's consent is withdrawn (`unlinkVisitorIdentityOnWithdrawal` clears `identified_contact_id`, §5 above), a later score recalculation no longer counts that visitor's engagement signal at all — the scoring engine has no separate consent-awareness logic of its own; it simply reads whatever `identified_contact_id` currently is, so it inherits the same withdrawal/suppression guarantees `POST /track/identify`/`POST /track/consent` already enforce, for free.
- **Dashboard v1 (Milestone 3.5) — no new privilege, aggregate-only exposure**: `/dashboard`'s five read paths (`getDealDashboardMetrics`, `listDeals`, `getLeadScoreDistribution`, `getHighScoreContacts`, `getIdentifiedVisitorMetrics`) introduce no new permission, no `SECURITY DEFINER` function, and no service-role bypass — every call is an ordinary tenant-scoped domain-layer query under the caller's own already-resolved `organizationId`, reusing the existing `deals:read`/`contacts:read` grants. The two contact-facing reads structurally cannot double-count a contact's historized `lead_scores` rows (`DISTINCT ON (contact_id)`, latest row only) and expose only a fixed, minimal field set — name/email/score/grade/computed-at — never a scoring-rule breakdown, raw enrichment payload, or scoring-rule internals. The visitor read inherits every existing consent/withdrawal/erasure guarantee for free, by construction: it counts a visitor only while `identified_contact_id` is currently non-null, so `unlinkVisitorIdentityOnWithdrawal` and `execute_contact_erasure()`'s own suppression (both above) remove that visitor from the dashboard's count the instant either fires, with no separate consent-awareness logic of its own. No `anonymousId`/`websiteVisitorId`/raw tracking metadata/IP/organizationId is ever rendered.
- **Data residency**: Supabase project hosted in an EU region given the EU customer base — avoids cross-border transfer complications for the majority of expected personal data.
- **Processor agreements**: every third-party processor touching personal data (email provider, enrichment provider, AI model providers, and — new with the Brain — the email inbox sync provider and meeting transcription provider) must have a Data Processing Addendum in place before integration; this is a procurement gate, not just an engineering concern, tracked in `docs/adr/` or a dedicated vendor register as the vendor list solidifies.
- **Right to rectification**: standard CRM edit flows satisfy this for contact-controlled data; portal users get a self-service profile edit as part of the Customer Portal (Phase 6).
- **Aggregation risk**: because the Brain's entire purpose is connecting signal across sources, a single tenant-scoping bug in its retrieval path (e.g., a semantic search missing an `organization_id` filter) has a larger blast radius than an equivalent bug anywhere else in the platform. `brain.semantic_search` results are filtered by `organization_id` at the query level *and* re-checked at the application layer before being returned to any persona — explicit defense-in-depth for this specific risk (`11-AI-Revenue-Brain.md` §10).

### 5.1 M1.6 implementation scope

The erasure cascade described above is real and enforced (`preview_user_erasure`/`execute_user_erasure`, `03-Database-Architecture.md` §2.8), scoped narrowly on purpose:

- **Subject**: at M1.6 ship time, only `data_subject_requests.subject_type = 'user'` (a staff `public.users` row) was executable — no `contacts`/`visitors`/`portal_users` existed yet, so this milestone proved the mechanism against the one real personal-data table the platform had at the time. **Since extended**: `subject_type = 'contact'` gained a real erasure cascade in Milestone 2.1C (`preview_contact_erasure`/`execute_contact_erasure`, mirroring the `user` pair exactly) and API dispatch in Milestone 2.1F-C (`docs/13-Technical-Design-Review.md` "Milestone 2.1"). `visitor`/`portal_user` remain schema-valid but unfulfilled, since neither table exists yet. `access`/`export` request types are schema-valid but unfulfilled for every subject type.
- **Dry-run before destroy**: `POST .../preview` never mutates data and reports the exact planned effect (or blocker) before `POST .../execute` is ever called; execute independently re-validates from scratch and does not trust a prior preview result — this is what makes the irreversibility of execution a deliberate, informed act rather than a one-shot risk.
- **Sole-admin blocker**: erasure is refused (409, not a silent no-op) if the target is the only active `org_admin` of any organization, surfaced by preview before any destructive action and re-checked independently by execute.
- **Auth identity removal**: a completed erasure deletes the linked Supabase Auth identity (`auth.users`), not just the `public.users` row — verified empirically against the local Auth schema's own internal cascade (`identities`/`sessions`/`refresh_tokens`/etc., all `ON DELETE CASCADE`) and proven by a real post-erasure login attempt failing in the test suite. A person cannot authenticate after a completed erasure.
- **Permissions**: `consent:record`, `data-subject-requests:create/read/execute` are `org_admin`-only in M1.6 — no agency-scoped role (`agency_owner`/`agency_admin`) has any access to compliance data yet; agency-facing compliance workflows are explicitly deferred until scoped separately.
- **SLA-breach detection**: `data_subject_request_breaches` (a view: `due_at < now() and status <> 'completed'`) is queryable and tested, but has no notification channel (email/Slack/Sentry) wired to it — that lands with the observability/alerting milestone, not here.

### 5.2 Milestone 4.1 Phase 1 implementation scope — Brain database + GDPR foundation

Six new tenant-scoped tables (`03-Database-Architecture.md` §2.9), all RLS-enabled, none exempt from the two-layer grant+policy discipline (§2 above):

- **Tenant isolation is structural, not only RLS**: every Brain FK carrying a tenant-owned parent (`brain_entity_profiles`→`contacts`/`companies`/`deals`, `brain_entity_profile_history`→`brain_entity_profiles`, `brain_embedding_entity_refs`→`brain_embeddings`/`contacts`/`companies`/`deals`, `brain_embeddings`→`brain_knowledge_documents`) is a real **composite** `(organization_id, id)` FK, not a plain id reference — adversarially verified: a same-org row cannot be attached to a different organization's parent via any of these FKs, independent of RLS. `deals` gained a `unique(organization_id, id)` constraint as the prerequisite this required (mirroring the identical `contacts` precedent).
- **Grants**: `authenticated` has ordinary `SELECT`/`INSERT`(/`UPDATE` where the row is mutable) on five of the six tables — no `DELETE` grant anywhere; rows are removed only via `ON DELETE CASCADE` or the erasure function below. `brain_knowledge_documents` is the one exception: `authenticated` has **SELECT only**. `anon` has zero grants on every Brain table.
- **`brain_knowledge_documents` write restriction**: `content_text` is free text with no deterministic entity linkage — it cannot participate in the DSR erasure cascade the way an FK-linked table can. Rather than open an ordinary RLS-scoped write path with no validation and no erasure coverage, this table ships **schema-only**: no INSERT/UPDATE grant, no application/API/UI code that writes to it. A later milestone needs a compliant ingestion/DSR design — most likely a narrow `SECURITY DEFINER` write path with real content validation — before this table becomes writable.
- **`execute_contact_erasure()` extended (targeted-capture design)**: the function now captures every `brain_embeddings` id linked to the target contact (via `brain_embedding_entity_refs`) **before** the contact delete fires — while the linking evidence still exists, not rediscovered afterward from whatever a cascade happens to leave behind. `brain_entity_profiles`/`brain_entity_profile_history`/`brain_embedding_entity_refs` rows for the contact are removed structurally by their own `ON DELETE CASCADE` FKs. Each captured `brain_embeddings` row is then deleted **in full** — the entire shared artifact, not merely the contact's own ref on it — even when a company/deal ref on the same chunk also exists: Phase 1 has no deterministic way to prove which substring of a shared `chunk_text` belongs only to the erased contact, so privacy safety takes precedence over preserving the shared artifact; a future ingestion system may regenerate a safe, contact-free replacement later. An unrelated embedding — including one that happens to have zero entity refs for an unrelated reason (e.g. in-flight ingestion) — is never reachable by this delete, because it is scoped to the pre-captured id set, never to "currently has no refs." Both properties (full-artifact deletion on match; zero reach on non-match) were adversarially verified against real Postgres, including a hostile fixture with synthetic PII (name/email/phone) in a shared chunk that a naive "purge only if now-orphaned" design had left recoverable — the shipped design does not.
- **`preview_contact_erasure()` deliberately not extended** — it stays a minimal `(can_proceed, blocker_reason, target_contact_id)` check, matching the established precedent that neither prior cascade extension (2.3A, 3.2F) touched it either.
- **Retention**: `brain_entity_profiles`/`brain_entity_profile_history`/`brain_embeddings`/`brain_embedding_entity_refs` registered in `data_retention_policies` (2555-day platform default). `brain_knowledge_documents` (no write path, see above) and `brain_sync_state` (a cursor/watermark, no personal data) are deliberately excluded, mirroring the `tags`/`taggings` precedent.
- **Future ingestion invariant, documented not enforced**: `brain_entity_profiles.profile` (jsonb) carries no schema-level constraint yet preventing a company/deal profile from embedding a specific contact's personal data — the migration's own comment documents the invariant a future ingestion design must honor (deterministic contact provenance or no cross-entity PII at all) before this column is ever populated; not a live risk today, since nothing writes to it yet.
- **Scope boundary**: no embedding is generated, no vector index exists, no semantic search reads any Brain table, `packages/brain` does not exist, and no ingestion of any kind is wired up — this milestone is schema plus GDPR erasure integration only (`docs/13-Technical-Design-Review.md` "Milestone 4.1 Phase 1").

## 6. Audit Logs

- `audit_logs` is append-only — no `updated_at`/`deleted_at`, entries are never mutated after creation, satisfying both security-audit and GDPR accountability requirements simultaneously.
- Logged actions include: authentication events (login, MFA challenge, API key creation/revocation), permission changes (role/membership changes), all `data_subject_requests` lifecycle transitions, agency roll-up view access, **agent approval-gate resolutions (a proposed action confirmed or discarded, and by whom)**, and any write action tagged as sensitive (deal amount changes, proposal sends, consent withdrawals).
- Each entry captures actor, action, resource type/id, before/after state (jsonb), IP address, and timestamp — sufficient to reconstruct "who did what, when, and what changed" without needing to correlate across multiple systems.
- Audit logs are themselves tenant-scoped (`organization_id`) for tenant-visible history (e.g., an org admin reviewing their own team's activity) but also queryable at the platform level for security investigations, via a separate, explicitly-audited platform-operator access path.
- **M1.6 implementation**: append-only is enforced at the grant level, not just by omitting an `UPDATE`/`DELETE` policy — `authenticated` has no `UPDATE`/`DELETE` grant on `audit_logs` at all, which fails closed with a permission error rather than relying on RLS policy coverage alone (the same two-layer discipline established in M1.2, `docs/03-Database-Architecture.md` §5). Actions actually logged as of M1.6: `consent.recorded`, `data_subject_request.created`, `data_subject_request.executed` — each written inside the same database transaction as the action it describes, never as a separate follow-up write. Authentication events (login) are **not yet wired** — doing so from `packages/auth` would create a package dependency cycle (`compliance` depends on `auth`, not the reverse, per `02-Software-Architecture.md` §4), so it's deferred rather than solved with an architecturally awkward workaround. The platform-level query path named above still does not exist as of M1.6.

## 7. Secrets Management

- Environment secrets (API keys, DB service-role credentials, signing secrets) stored in Vercel Environment Variables and Supabase Vault — scoped per environment (dev/staging/prod), never shared across environments.
- No secret is ever committed to the repository; `.env.example` documents required variable names with placeholder values only.
- CI/CD pipelines inject secrets at build/deploy time from the platform's secret store, not from repository configuration files.
- Access to production secrets is limited to the minimum set of people/systems that require it; as the team grows beyond the solo-founder phase, this becomes a formally reviewed access list rather than implicit trust.

### 7.1 M1.8 implementation scope

The "structured logging redacts secret/PII-shaped fields" and "error-tracking service" statements above are now real, not aspirational, as of M1.8:

- **Structured logging**: `apps/web/app/api/v1/_shared/logger.ts` — one JSON log line per request (`timestamp`, `level`, `method`, `route`, `status`, `durationMs`, `actorId`/`organizationId` where already resolved, a developer-authored `message`, an optional coarse `errorType`), emitted to stdout (Vercel's own Runtime Logs is the sink — no new log-aggregation vendor). Raw request bodies, full headers, and cookies are never accepted as parameters in the first place — there is no field for them to flow through, not just a redaction rule hoping to catch them after the fact. A runtime allowlist (`ALLOWED_KEYS`) additionally strips any field not on this explicit list, defending against a caller bypassing the type system.
- **Redaction**: `apps/web/app/api/v1/_shared/redaction.ts` — one shared implementation used identically by the structured logger and Sentry's `beforeSend`/`beforeSendTransaction` hooks, so there is exactly one place the rule set is defined. Two complementary mechanisms, both required: **pattern-based** (`redactString`) matches known secret shapes wherever they appear in string content — `arev_live_`/`arev_test_` API keys, `Bearer` tokens, JWT-shaped values, `sk_`/`pk_` provider keys, credentials embedded in a DB connection string, email addresses, `name=value`-shaped session/cookie strings — and **key-name-based** (`SENSITIVE_KEY_PATTERN` inside `redactDeep`) redacts the *entire* value at any key literally named `cookie`/`cookies`/`set-cookie`/`authorization`/`password`/`secret`/`session`, regardless of that value's own shape. The key-based rule exists because pattern-matching alone was proven, empirically, insufficient: Sentry's own `RequestData` integration auto-parses a raw `Cookie` header into a structured `request.cookies` object keyed by cookie name (e.g. `{ "sb-access-token": "<raw value>" }`), where the value alone has no "name=value" string shape for a pattern rule to catch — found and fixed during this milestone's own verification, not assumed safe because `sendDefaultPii: false` was set.
- **Error tracking**: Sentry (`@sentry/nextjs`), server and Next.js Edge middleware runtimes only — **no browser/client-side capture, no session replay, no tracing/APM** (`tracesSampleRate` deliberately omitted). `sendDefaultPii: false` explicitly set (not relied on as an assumed default). Every outgoing event passes through the shared redaction function via `beforeSend`/`beforeSendTransaction` before it would leave the process — verified empirically using Sentry's own supported test mechanism (a custom `transport` capturing outgoing envelopes instead of sending them over the network), not assumed correct because the SDK was installed.
- **No Supabase Edge Function exists in this codebase as of M1.8** (verified by direct search) — only `apps/web`'s Node server runtime and Next.js's own Edge runtime (middleware) are instrumented. The milestone's original text ("wired into apps/web and Edge Functions") presupposed a Supabase Edge Function that doesn't exist yet; the only candidate — a scheduled outbox-dispatcher Edge Function — was itself an explicitly deferred M1.7 gap (`02-Software-Architecture.md` §5). Edge Function instrumentation remains deferred until one exists, not silently dropped. **Milestone 3.3 update**: the scheduled-dispatch gap itself is now closed, but not by a Supabase Edge Function — `GET /api/internal/dispatch-events` (`04-API-Architecture.md` §2.8) is a Vercel Cron-invoked `apps/web` API route, the same Node server runtime already instrumented above. No Supabase Edge Function exists in this codebase as of Milestone 3.3 either.
- **Dependency vulnerability remediation performed as a prerequisite**: before enabling the CI dependency-scan gate (§10.1), the repository's actual baseline was checked first rather than assumed clean — found 24 known vulnerabilities (1 critical, 13 high, 10 moderate), all in devDependencies (`next`, `vitest`, and transitive build tooling). Remediated via in-major-line version bumps (`next` 15.1→15.5.23, `vitest` 2.1→3.2.7 — no 2.x fix existed for the critical `vitest` UI-server arbitrary-file-read finding) plus targeted `pnpm.overrides` for deep transitive packages (`postcss`, `sharp`, `js-yaml`, `esbuild`, `vite`, two independently-versioned `brace-expansion` lines). Full local test suite re-verified green after each change; zero known vulnerabilities at any severity as of this milestone's closeout.

## 8. Backup Strategy

- **Database**: Supabase automated daily backups with point-in-time recovery (PITR) enabled once on a plan that supports it — target RPO (recovery point objective) of under 24 hours at MVP, tightening to PITR-level (minutes) as the platform carries paying-customer data.
- **Storage** (proposal PDFs, uploaded documents, brand assets): replicated per Supabase Storage's underlying durability guarantees; critical generated artifacts (sent proposals) are also referenced by immutable URL so a regenerate-on-demand path exists independent of backup restore.
- **Workflow definitions**: n8n workflow JSON exports are version-controlled in the monorepo (`workflows/`), so the automation layer itself is recoverable from git independent of the running n8n instance's own state.
- **Backup verification**: periodic restore drills (initially manual, automated once release cadence justifies it) to confirm backups are actually restorable, not just "backups exist."

## 9. Disaster Recovery

- **Defined tiers**: full regional Supabase/Vercel outage (low likelihood, vendor-managed failover) vs. data corruption/accidental deletion (higher likelihood, requires our own runbook) vs. n8n instance failure (automation-only outage, core CRM remains available since n8n is not on the read/write critical path for core CRM data).
- **In-flight agent runs**: because agent execution is queued/worker-based, not inline (`02-Software-Architecture.md` ADR-005), an `agent_runs` row's state (`queued`/`running`, plus its `agent_tool_calls` history) is durably persisted in Postgres, not held only in an ephemeral process — a worker crash or restart resumes or cleanly re-queues an in-flight run from its last persisted state rather than losing it silently.
- **RTO/RPO targets** (MVP-stage, revisited as the customer base grows): RTO (recovery time objective) of a few hours for a full platform outage; RPO aligned to the backup cadence in §8.
- **Runbooks**: documented recovery steps for the most likely failure modes (accidental tenant data deletion via `data_subject_requests` misconfiguration, n8n instance crash, provider API outage cascading into stuck `workflow_runs`) — maintained in `docs/runbooks/` as they're written, not left as tribal knowledge. First one written: `docs/runbooks/auth-users-reconciliation.md` (M1.3) — detection/remediation if `auth.users` and `public.users` ever diverge, though the sync trigger's atomicity and the FK's `on delete cascade` make this structurally unlikely outside manual DB intervention.
- **Graceful degradation**: because n8n is architecturally isolated (`02-Software-Architecture.md`), an n8n outage degrades to "automation/enrichment/email paused" rather than taking down core CRM read/write functionality — this isolation is itself a DR strategy, not just a modularity choice.
- **Incident communication**: tenant-facing status communication (in-app banner + status page, introduced once customer count justifies the overhead) so agencies can inform their own end clients during an incident rather than being blindsided.

## 10. Vulnerability Management

- **Dependency scanning**: automated dependency/supply-chain vulnerability scanning (e.g., Dependabot or equivalent) runs in CI from Phase 1 — cheap to set up early, expensive to retrofit onto an already-large dependency tree later.
- **Disclosure policy**: a lightweight, published vulnerability disclosure policy (a security contact and a stated response-time commitment) exists from the point the platform has its first real external users — not deferred to enterprise-readiness, since a disclosure channel costs little to stand up and its absence is itself a bad signal to a security-conscious prospect.
- **Penetration testing**: a formal third-party penetration test is a Phase 7 (Enterprise) milestone, ahead of the first enterprise contract or SOC2 readiness push — consistent with SOC2 itself being a stated future milestone, not an MVP blocker, but named here explicitly so it isn't lost track of.

### 10.1 M1.8 implementation scope

- **Dependency scanning is now real, not aspirational**: `pnpm audit --audit-level=high` runs as a CI step in `.github/workflows/ci.yml` and genuinely fails the build on a known high/critical finding (`docs/10-CLAUDE.md` §8's existing "merge blocker" rule, mechanically enforced for the first time) — proven via the TDR's required pin-and-revert exercise (a known-vulnerable version was temporarily pinned, confirmed to fail the gate, then reverted; nothing vulnerable was left committed). `.github/dependabot.yml` separately opens scheduled update PRs for `npm`/pnpm and GitHub Actions — a human reviews and merges every update, no auto-merge configured.
- **Disclosure policy published**: `SECURITY.md` at the repo root — reporting channel, scope, safe-harbor language, and response-time commitments (acknowledgement within 3 business days, initial assessment within 10).
