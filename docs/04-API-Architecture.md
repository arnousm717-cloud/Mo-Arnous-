# 04 — API Architecture

## 1. Design Principles

- REST over Next.js Route Handlers, resource-oriented, versioned from day one (`/api/v1/...`) — a breaking change ships as `/api/v2` alongside `v1`, never an in-place break.
- Every endpoint is tenant-scoped by default; there is no endpoint that returns data across organizations without going through the explicit agency-rollup path (see `03-Database-Architecture.md` §5).
- The API is provider-agnostic at the boundary: internal endpoints never leak which external provider (email sender, enrichment API) fulfilled a request.
- JSON in, JSON out. `snake_case` field names to match the database layer directly (no case-translation layer to maintain) — an accepted tradeoff, not a free one: this couples the public wire format to internal schema naming, so an internal rename that must not break external callers needs a deliberate compatibility shim at the route-handler level, not a global find-and-replace.
- **Error responses use one consistent envelope** across every endpoint: `{ "error": { "code": "<ApiErrorCode>", "message": "human-readable, safe to display", "request_id": "<uuid>" } }`. **Implemented platform-wide as of Milestone 2.5A** (`apps/web/app/api/v1/_shared/api-error.ts`, `buildApiErrorBody`/`apiError` — the one canonical constructor every route's `handlers.ts`/`route.ts` uses; no route builds an error body inline). Before 2.5A this section described the intended shape while every shipped route (M1.4 through M2.3D) actually emitted a flat `{ "error": "<string>" }` — that discrepancy is what 2.5A closed, converging the code on this documented contract rather than the other way around.
  - `code` is one of a small, closed, stable vocabulary — never a route-specific or per-message code: `UNAUTHENTICATED` (401), `FORBIDDEN` (403, including a same-origin/CSRF rejection), `NOT_FOUND` (404), `VALIDATION_ERROR` (400), `CONFLICT` (409, a genuine business-rule conflict — e.g. a duplicate active tag name, or the sole-`org_admin` DSR-erasure blocker), `IDEMPOTENCY_CONFLICT` (409, specifically an `Idempotency-Key` reused with a different request body — the one case with two possible codes at the same status, disambiguated by which situation actually occurred), `INTERNAL_ERROR` (500, generic, no internal detail).
  - `message` is always a string already safe to display — either a short, developer-authored literal (`"Not found"`, `"Unauthorized"`) or a domain `ValidationError`-family class's own message (`packages/crm`'s typed errors); never a raw caught exception, SQL error, or stack trace.
  - `request_id` is a fresh `crypto.randomUUID()` generated per error response — non-empty on every error response, always present. There is no request-scoped correlation-id mechanism elsewhere in this repository (e.g. threaded into `_shared/logger.ts`'s structured log line) as of 2.5A — each error response's `request_id` is self-contained, meant for a client to report back, not (yet) guaranteed to match its own server-side log line verbatim. Extending this to real cross-cutting request correlation is a possible future enhancement, not part of 2.5A's scope.
  - **The HTTP status code remains authoritative and is never inferred from `code`** — the envelope only describes *what kind* of error occurred at whatever status the route already returns; changing the envelope shape did not change any route's status-code behavior.
  - **Successful response shapes are entirely unaffected** — this convention governs error responses only; every `2xx` body (`{ company }`, `{ companies: [...], nextCursor }`, etc.) is unchanged.
- **Idempotency keys are supported on mutating requests where the organization-scoped idempotency model is structurally applicable** (`POST`/`PATCH`), via an `Idempotency-Key` header; documented exclusions apply. A retried request with the same key against the same endpoint returns the original result rather than creating a duplicate — this is what makes a client's network retry safe, and its absence would otherwise mean a flaky connection can silently duplicate a deal or contact. **Concrete contract, as actually implemented (Milestone 2.1F-A, `public.idempotency_keys`)**: the header is **optional**, not required — a request without one is simply not deduplicated, never rejected. Same key + identical request body → the original response is replayed byte-for-byte, the mutation is never re-executed. Same key + a *different* request body → `409 Conflict` (`{ "error": { "code": "IDEMPOTENCY_CONFLICT", "message": "Idempotency-Key already used with a different request", "request_id": "b3c1e2a0-4f5d-4a11-9c2e-7d8f6a1b2c3d" } }`), never silently applied as a second write. Keys are scoped per organization (never collide across tenants) and expire after **24 hours**, after which the same key becomes reusable. Neither the raw header value nor the raw request body is ever persisted — only SHA-256 hashes/fingerprints. **Since wired into live routes (Milestone 2.1F-B)**: `POST`/`PATCH /api/v1/companies` and `/api/v1/contacts` are the actual, shipped consumers of this mechanism — see §2.4.
- **Pagination is cursor-based** on every list endpoint (`?cursor=...&limit=...`, default `limit=25`, max `100`), ordered by `created_at` descending unless a resource states otherwise. Offset pagination is not used, to avoid the well-known page-drift problem under concurrent writes.

Standard verbs apply per resource: `GET` (list/detail), `POST` (create), `PATCH` (partial update), `DELETE`. No resource uses `PUT` — partial updates only, to avoid accidental full-object overwrites. **`DELETE` on an ordinary CRM resource (`contacts`, `companies`, `deals`, `proposals`) is the recoverable soft-delete described in `03-Database-Architecture.md`'s deletion model — it does not, by itself, satisfy a GDPR erasure obligation.** That is only ever fulfilled via the dedicated `POST /api/v1/data-subject-requests/{id}/preview` then `POST .../execute` pair (§2.2), not `DELETE` on the resource — a deliberate deviation from this section's own verb convention, made explicitly in M1.6 (Decision D) because a single `DELETE` call reads as symmetric with every other resource's recoverable soft-delete, which an irreversible cross-cascade hard-delete is not. This distinction is stated explicitly here because conflating the two is one of the most common real-world compliance mistakes in CRM-shaped APIs.

### 2.1 `/api/v1/organizations` — implemented contract (M1.4)

The first resource actually built beyond the health check, so its real contract is recorded here rather than left to match the general table above by assumption.

- **`GET /api/v1/organizations`** — session auth only (no API-key path yet). Response shape is always `{ organizations: [...] }`, never a bare array, so the envelope can carry pagination/metadata later without a breaking change. What's returned depends entirely on server-resolved context, never a query parameter:
  - `agency_owner`/`agency_admin` → every client organization under their agency, via the `agency_rollup_organizations` view (`03-Database-Architecture.md` §5) — never a broadened query against the base `organizations` table.
  - An ordinary org-level user → their own single organization, as a one-item array.
  - An authenticated user with neither (no membership at all yet) → `{ organizations: [] }`, not an error — same "route to onboarding" philosophy as `get_my_membership_context()`.
  - No authenticated session at all → `401`.
  - A user holding both an agency-level and an organization-level membership gets the agency view — agency context takes precedence when present.
- **`POST /api/v1/organizations`** — creates a client organization under the caller's own agency. `201` with `{ organization: { id, name, slug } }` on success.
  - `403` if the caller isn't an active `agency_owner`/`agency_admin` of some agency — includes ordinary org-level users and unauthenticated-but-somehow-past-401 edge cases alike.
  - `agency_id` is **never** read from the request body — it comes exclusively from the caller's server-resolved agency membership. A body field named `agencyId` is silently ignored; it cannot be used to target a different agency (verified by test).
  - `400` for a missing/empty/non-string `name`, or a `name` over 200 characters. `400` for a malformed JSON body.
  - Slug collisions are handled transparently server-side (the same generate-and-retry-on-conflict pattern as individual-user org signup) — a client never sees a slug conflict; two organizations may share the same `name`, they just get distinct auto-generated slugs.
  - `500` (generic, no internal detail) only if organization creation fails for a reason other than the above — e.g. the slug-retry budget is exhausted, astronomically unlikely in practice.
  - A same-origin check on the `Origin` header (when present) returns `403` for a cross-origin `POST`, as defense-in-depth alongside the session cookie's own `sameSite: "lax"` default.
  - **No `Idempotency-Key` support (Milestone 2.5B, deliberate, not an oversight)**: the caller here is agency-scoped (`agencyId`, no `organizationId` — the organization being created doesn't exist yet at request time), and `idempotency_keys.organization_id` is `NOT NULL`. Retrofitting would require a schema change (a nullable `organization_id` and a new tenant-scoping column/policy), out of scope for a mechanical Idempotency-Key retrofit — reported as a blocker during 2.5B's audit rather than worked around.

### 2.2 `/api/v1/consent`, `/api/v1/data-subject-requests` — implemented contract (M1.6)

- **`POST /api/v1/consent`** — session auth, `org_admin` only (`08-Security.md` §3.1). Body: `subjectType` (`contact`/`visitor`/`portal_user`), `subjectId`, `consentType` (`marketing_email`/`cookie_tracking`/`data_processing`), `status` (`granted`/`withdrawn`), optional `source`. `201` with `{ consent: { id, status, recordedAt } }`. `organization_id` comes exclusively from the caller's server-resolved context. **`Idempotency-Key` supported (Milestone 2.5B)** — see below.
- **`POST /api/v1/data-subject-requests`** — session auth, `org_admin` only. Body: `subjectType` (`contact`/`visitor`/`portal_user`/`user`), `subjectId`, `requestType` (`access`/`export`/`delete`). `201` with `{ dataSubjectRequest }` on success. `400` if `requestType` isn't `delete` — `access`/`export` are schema-valid but have no fulfillment logic in M1.6. **`Idempotency-Key` supported (Milestone 2.5B)** — see below.
- **`GET /api/v1/data-subject-requests/{id}`** — session auth, `org_admin` only, scoped to the caller's own organization via RLS (a cross-org id returns `404`, not `403`, to avoid confirming the row's existence to a caller who can't see it).
- **`POST /api/v1/data-subject-requests/{id}/preview`** / **`POST /api/v1/data-subject-requests/{id}/execute`** — dispatch on `subject_type` (M2.1F-C). The DSR is fetched tenant-scoped (RLS: `organization_id = current_org()`) before any dispatch decision — a cross-org or nonexistent `{id}` is a plain `404`, identical either way, and `subject_type` is read exclusively from that server-fetched row, never from the request body/query/header. `subject_type='user'` dispatches to `previewUserErasure`/`executeUserErasure` (`200` with `{ preview: { canProceed, blockerReason, targetUserId, membershipCount, affectedOrganizationIds } }` / `{ result: { targetUserId, membershipsRemoved, completedAt } }`); `subject_type='contact'` dispatches to `previewContactErasure`/`executeContactErasure` (`200` with `{ preview: { canProceed, blockerReason, targetContactId } }` / `{ result: { targetContactId, completedAt } }`); `subject_type` of `visitor`/`portal_user` is schema-valid but has no fulfillment logic and returns `400` without invoking any erasure function. Preview never mutates — a `false` `canProceed` is still a `200`, a successful preview reporting a blocker, not a failed request. Execute is irreversible and independently re-validates authorization (and, for `user`, the sole-`org_admin` blocker) inside its own `SECURITY DEFINER` SQL function; it never trusts a prior `preview` call. `409` if blocked or already completed. Both endpoints share the same `data-subject-requests:execute` RBAC check as before M2.1F-C — no new permission was introduced.
  - **`/preview`: no `Idempotency-Key` support (Milestone 2.5B, deliberate, not an oversight)** — confirmed read-only, deterministic, side-effect-free (`previewUserErasure`/`previewContactErasure` delegate to `SECURITY DEFINER` functions that never mutate `data_subject_requests`/`users`/`memberships`/`contacts`). There is no side effect to deduplicate.
  - **`/execute`: `Idempotency-Key` supported (Milestone 2.5B)** — the highest-sensitivity route in this milestone's scope. See below for the atomicity design this required.

**Idempotency-Key design (Milestone 2.5B).** Reuses `apps/web/app/api/v1/_shared/idempotency.ts` unchanged — same SHA-256 key hashing, method/route/body fingerprinting, 24h TTL, organization-scoped uniqueness, replay/409-conflict semantics, and auth-before-replay ordering as every other resource (§1). What's new: `recordConsent`, `fileDataSubjectRequest`, `executeUserErasure`, and `executeContactErasure` (`packages/compliance`) each gained an optional trailing `existingClient?: PoolClient` parameter — omitted, each opens its own transaction exactly as before 2.5B; supplied, the mutation runs on that same client so the idempotency reservation, the mutation, and the reservation's own completion commit or roll back together as one atomic unit. This mirrors `packages/crm`'s own established pattern for its create/update functions exactly; the shared helper (`runInClientOrTransaction`) was generalized from `packages/crm` into `@ai-revenue-os/database` (both packages already depend on it) specifically so neither package needed a new dependency on the other. `executeUserErasure`/`executeContactErasure`'s own `SECURITY DEFINER` SQL functions, their validation, and their independent "already completed" rejection are entirely unchanged — only which connection they run on. On `/execute`, a business-rule rejection (e.g. the sole-`org_admin` blocker) is never cached/replayed — it propagates out of the idempotency callback, rolling back the reservation entirely, so a retry is always freshly (and fairly) re-evaluated rather than replaying a stale denial.

### 2.3 `/api/v1/api-keys` — scope clarification (M1.7)

The resource-map row for API Keys above (§2) describes the **eventual, Phase 7 self-service shape** ("Issue, list, revoke scoped keys for the calling organization"), not what exists today. As of M1.7:

- There is **no `/api/v1/api-keys` route at all** — no HTTP surface, tenant-facing or otherwise.
- `api_keys` (`03-Database-Architecture.md` §2.1) is a real table, and a key can be issued, but only via a local, human-run script (`packages/database/scripts/issue-api-key.mjs`) using `DATABASE_URL` directly — never reachable from `apps/web` (verified by an automated coverage test, `api-key-issuance-isolation.test.ts`).
- Nothing in the request-handling pipeline validates a `Bearer` token yet — `resolveRequestContext()` only resolves session auth. API-key-based request authentication is deferred to Phase 3, when n8n becomes the first real caller (`06-n8n-Workflow-Architecture.md` §1), rather than built ahead of any actual consumer.
- This section exists so the gap between the resource-map's description and reality is explicit, not discovered by surprise — the same treatment M1.6 gave the `data_subject_requests` verb correction (§2.2 above).

### 2.4 `/api/v1/companies`, `/api/v1/contacts` — implemented contract (M2.1F-B)

Session auth only (no API-key path yet, same as every other route above). Error envelope is the structured `{ "error": { "code", "message", "request_id" } }` form (§1) — flat `{ "error": "<string>" }` before Milestone 2.5A, converged on the structured contract by that milestone, not by re-editing this description.

- **Tenant/RBAC resolution**: identical chain for every verb on both resources — `getAuthenticatedUser()` → `resolveOrganizationContextForUser(userId)` → construct an org-scoped `Actor` → `can(actor, permission)` (`companies:read/create/update/delete`, `contacts:read/create/update/delete`, `05-AI-Agent-Architecture.md`/`08-Security.md` RBAC matrix, unchanged from 2.1E). `organization_id` is never accepted from the request body, query string, header, or path — only from server-resolved context. No session → `401`. A resolved session with no usable org context (including a purely agency-scoped actor, who gets no direct CRM access) → `403`.
- **`GET /api/v1/companies`** / **`GET /api/v1/contacts`** — `{ companies: [...], nextCursor }` / `{ contacts: [...], nextCursor }`. Cursor-based pagination only (`packages/crm`'s existing cursor implementation) — no offset, no free-text search. Filters: `ownerId` (companies); `companyId`, `ownerId`, `lifecycleStage` (contacts). A malformed `cursor`, an invalid `limit`, or an invalid `lifecycleStage` filter value → `400`.
- **`POST /api/v1/companies`** — body: `name` (required), `domain`, `industry`, `employeeCount`, `annualRevenue`, `linkedinUrl`, `ownerId` (all optional). `201` with `{ company }`.
- **`POST /api/v1/contacts`** — body: `companyId`, `firstName`, `lastName`, `email`, `phone`, `jobTitle`, `linkedinUrl`, `lifecycleStage`, `ownerId` (all optional at the HTTP layer; `packages/crm`'s identity-invariant rule — at least one of `firstName`/`lastName`/`email` — is enforced downstream, not re-implemented here). `201` with `{ contact }`.
- **`GET /api/v1/companies/{id}`** / **`GET /api/v1/contacts/{id}`** — `{ company }` / `{ contact }`, `200`. A cross-org id, a genuinely nonexistent id, and (as of **Milestone 2.5C**) a malformed (non-UUID-shaped) id are **indistinguishable** — all `404`, identical `code`/`message` — same "don't confirm a foreign tenant's row exists" rule as `data-subject-requests/{id}` (§2.2), now extended by 2.5C to a third case using the same `isValidUuid` shared check §2.6 already established for Activities/Notes/Tags/Taggings.
- **`PATCH /api/v1/companies/{id}`** / **`PATCH /api/v1/contacts/{id}`** — same field sets as the respective `POST`, all optional; an omitted field is left unchanged (partial update), never coerced into an explicit `null`. `200` with the updated resource; `404` per the same cross-org/nonexistent rule above.
- **`DELETE /api/v1/companies/{id}`** / **`DELETE /api/v1/contacts/{id}`** — soft-delete only (`packages/crm`'s `softDeleteCompany`/`softDeleteContact`; never `packages/compliance`, never a physical `DELETE`). `200` with the now-soft-deleted resource (`deletedAt` populated). A subsequent `GET`/second `DELETE` on the same id → `404`, identical to any other absent row.
- **Errors**: `ValidationError` / `InvalidOwnerError` / `InvalidCompanyRelationshipError` → `400`; `DuplicateContactEmailError` → `409`; anything unexpected → `500` with no internal detail exposed. Mapping is done exclusively via `instanceof` checks against `packages/crm`'s typed error classes — never fragile message-substring matching.
- **Idempotency**: an optional `Idempotency-Key` header on `POST`/`PATCH` only (never `DELETE`, never `GET`) opts into the 2.1F-A `idempotency_keys` subsystem — a missing header simply performs the mutation directly, with no reservation. Full TTL/replay/conflict semantics are owned entirely by `apps/web/app/api/v1/_shared/idempotency.ts` (§ above, 2.1F-A) and are not duplicated in route code. Authorization (`resolveActor`) always runs **before** idempotency lookup, so a replay can never bypass a since-revoked permission — a caller demoted between the original request and a retry gets a fresh `403`, not a replayed success. For `PATCH`, the concrete resource id is part of the fingerprinted route identity (`/api/v1/companies/{id}`), so the same key reused against a different id is treated as a genuinely different request (`409`) rather than an accidental cross-resource replay.
- **Mass-assignment protection**: each route's field-allowlist extraction function has no code path at all for `id`, `organizationId`/`organization_id`, `deletedAt`, `createdAt`, `updatedAt`, or `enrichmentStatus` — an attacker-supplied value for any of these in the request body is silently discarded, not merely overwritten. Unknown/unsupported fields anywhere in the body are likewise silently ignored.
- **CSRF**: `POST`/`PATCH`/`DELETE` reuse the existing `isSameOrigin()` check (same mechanism as `/api/v1/organizations`, §2.1) — no new CSRF mechanism was introduced. `GET` remains unauthenticated-for-CSRF-purposes (read-only, no state change).
- **PII/logging**: request/response bodies (email, phone, name, LinkedIn URL), the `Idempotency-Key` header, and any persisted idempotency `response_body` are never written to structured logs — `StructuredLogFields` (`_shared/logger.ts`) has no field for any of them.

### 2.5 `/api/v1/deals`, `/api/v1/pipelines`, `/api/v1/pipelines/{id}/stages` — implemented contract (M2.2D)

Session auth only, structured `{ "error": { "code", "message", "request_id" } }` envelope (§1), cursor pagination, `isSameOrigin()` CSRF check — same conventions as §2.4, not repeated in full here. Domain logic (validation, relationship checks, status derivation, the default-pipeline invariant) lives entirely in `packages/crm`; every route here is a thin `route.ts` (HTTP extraction) + `handlers.ts` (auth/RBAC/domain call/error mapping) pair, reusing `resolveActor` from each resource's own top-level `handlers.ts` exactly like `companies/[id]/handlers.ts` reuses `companies/handlers.ts`'s.

- **Tenant/RBAC resolution**: identical chain to §2.4 — `getAuthenticatedUser()` → `resolveOrganizationContextForUser(userId)` → `can(actor, permission)`. `deals:read/create/update/delete` and `pipelines:read/create/update/delete` (M2.2C, `08-Security.md` §3.1). **`pipeline_stages` has no permission keys of its own** — every stage route checks the parent pipeline's own `pipelines:*` key (`GET`→`pipelines:read`, `POST`→`pipelines:create`, `PATCH`→`pipelines:update`, `DELETE`→`pipelines:delete`).
- **`GET /api/v1/deals`** — `{ deals: [...], nextCursor }`. Filters: `pipelineId`, `stageId`, `ownerId`, `companyId`, `status`. A malformed `cursor`/`limit`/`status` → `400`.
- **`POST /api/v1/deals`** — body: `pipelineId` (required), `stageId` (required), `companyId`, `primaryContactId`, `amount`, `currency` (default `EUR`), `probability`, `expectedCloseDate`, `ownerId` (all optional). **`status` is never a body field at all** — it is always derived server-side from the target stage's `is_won_stage`/`is_lost_stage` flags (M2.2B); a client-supplied `status` key is silently discarded, not merely overwritten. `201` with `{ deal }`.
- **`GET /api/v1/deals/{id}`** / **`PATCH /api/v1/deals/{id}`** / **`DELETE /api/v1/deals/{id}`** — same cross-org/nonexistent-indistinguishable `404` rule as §2.4, now also covering a malformed (non-UUID-shaped) `{id}` (**Milestone 2.5C**). `PATCH` accepts the same field set as `POST` (all optional, partial update); if `pipelineId` is changing to a genuinely different pipeline, `stageId` must be supplied in the same request (`400` otherwise — this API never guesses a replacement stage) and is validated against the *new* pipeline. `DELETE` is `packages/crm`'s `softDeleteDeal` only — never a physical `DELETE`.
- **`GET /api/v1/pipelines`** / **`POST /api/v1/pipelines`** — `{ pipelines: [...], nextCursor }` / `{ pipeline }`. `POST` body: `name` (required), `isDefault` (optional — accepted at create time only; `packages/crm`'s `createPipeline` already handles "create as default" transactionally). No list filters beyond cursor/limit (none required by the frozen design).
- **`GET /api/v1/pipelines/{id}`** / **`PATCH /api/v1/pipelines/{id}`** / **`DELETE /api/v1/pipelines/{id}`** — same `404` rule, now also covering a malformed `{id}` (**Milestone 2.5C**); the same applies to **`POST /api/v1/pipelines/{id}/set-default`**'s own path `{id}`. **`PATCH` accepts `name` only — there is no code path for `isDefault` in its extraction function at all**, so a client-supplied `isDefault` in a `PATCH` body has zero effect, silently. `DELETE` (`softDeletePipeline`) returns `409 Conflict` (`{ "error": { "code": "CONFLICT", "message": "cannot delete the organization's active default pipeline — call setDefaultPipeline to switch the default first", "request_id": "b3c1e2a0-4f5d-4a11-9c2e-7d8f6a1b2c3d" } }`) if the target is the organization's current active default — the same "syntactically valid request, rejected by current resource state" category as `DuplicateContactEmailError`.
- **`POST /api/v1/pipelines/{id}/set-default`** — the explicit default-switch contract this milestone required a decision on (no prior frozen HTTP decision existed). Calls `packages/crm`'s `setDefaultPipeline` (M2.2B: atomically unsets the old default, sets the new one). No request body. `200` with `{ pipeline }` (a no-op, still `200`, if the target is already the default). `404` if `{id}` doesn't resolve to an active pipeline in the caller's own organization (same role as any other path-identified resource's `:id` — contrast with `pipelineId` as a *body field* on `POST`/`PATCH /api/v1/deals`, which maps the identical `InvalidPipelineRelationshipError` to `400` instead, since there it's a relationship field, not a path resource identifier). `pipelines:update` RBAC (a default switch is pipeline management, not creation or deletion). Chosen over accepting `isDefault` in the generic `PATCH` specifically to avoid a hidden/implicit mutation path for a state change with real invariant implications — mirrors the existing `POST .../{id}/preview` / `POST .../{id}/execute` dedicated-verb-pair precedent already established for `data-subject-requests` (§2.2, M1.6 Decision D). **No `Idempotency-Key` support** — not one of this milestone's six enumerated idempotency routes (below), and the underlying operation is already naturally idempotent (a second call against an already-default pipeline no-ops).
- **`GET /api/v1/pipelines/{id}/stages`** / **`POST /api/v1/pipelines/{id}/stages`** — nested under a nonexistent, cross-org, or (as of **Milestone 2.5C**) malformed parent pipeline `{id}` → `404` for both verbs (an explicit parent-existence pre-check for `GET`, since an empty stages array would otherwise be genuinely ambiguous between "real pipeline, zero stages" and "no such pipeline"; `POST` relies on `createPipelineStage`'s own existence validation, mapped to `404`, avoiding a redundant duplicate query). `GET` returns `{ stages: [...] }` — a **plain array, not a cursor `Page`** (M2.2B's own documented deviation: stages are a small, `sort_order`-ordered, bounded-per-pipeline set, not an unbounded chronological list). `POST` body: `name` (required), `sortOrder` (required), `probability`, `isWonStage`, `isLostStage` (all optional). **A body `pipelineId` field, if present, is silently ignored — the stage is always created under the URL's `{id}`, never a body-claimed one.** `201` with `{ stage }`.
- **`GET /api/v1/pipelines/{id}/stages/{stageId}`** / **`PATCH .../{stageId}`** / **`DELETE .../{stageId}`** — **adversarially proven nested-resource IDOR safety**: a `stageId` that exists but belongs to a *different* pipeline than `{id}` (even a pipeline the caller legitimately owns in the same organization) returns the exact same `404` body (`{ "error": { "code": "NOT_FOUND", "message": "Not found", "request_id": "b3c1e2a0-4f5d-4a11-9c2e-7d8f6a1b2c3d" } }` — a *different* `request_id` on each actual response, never a literally identical one) as a genuinely nonexistent `stageId` or a cross-organization one — no distinguishing error, no "belongs to another pipeline" message, ever. This falls directly out of `packages/crm`'s own `getPipelineStageById`/`updatePipelineStage`/`softDeletePipelineStage` (M2.2B), which scope their lookup by `(organization_id, pipeline_id, id)` together in one query — no separate parent-existence check is needed or added here (adding one would duplicate domain validation for no additional safety). **Milestone 2.5C** extends this same indistinguishability to a malformed `{id}`, a malformed `{stageId}`, and both malformed at once — `isValidUuid` validates each independently, before either reaches a query. `PATCH` accepts `name`, `sortOrder`, `probability`, `isWonStage`, `isLostStage` — changing `isWonStage`/`isLostStage` to a genuinely different value cascades `deals.status` for every deal referencing that stage, in the same transaction (M2.2B), including soft-deleted deals. `DELETE` (`softDeletePipelineStage`) does **not** reject a stage still referenced by active deals — the frozen Milestone 2.2 decision that unrelated deal edits must keep working after pipeline/stage soft-delete.
- **Errors**: `ValidationError` / `InvalidOwnerError` / `InvalidCompanyRelationshipError` / `InvalidContactRelationshipError` / `InvalidPipelineRelationshipError` / `InvalidStageRelationshipError` → `400` on `/api/v1/deals` (relationship fields are all body fields there). On the Pipelines/Stages routes, `InvalidPipelineRelationshipError` instead means a path-identified resource doesn't resolve → `404` (see `set-default` and nested-stage `POST` above) — the same error class maps to a different status code depending on whether it names a body relationship field or a path resource, and each mapping is documented at its own call site. `CannotDeleteDefaultPipelineError` → `409`. Anything unexpected → `500`.
- **Idempotency**: `Idempotency-Key` wired on exactly six routes — `POST`/`PATCH /api/v1/deals`, `POST`/`PATCH /api/v1/pipelines`, `POST`/`PATCH /api/v1/pipelines/{id}/stages`(`/{stageId}`) — never on any `GET`, never on `DELETE` (matching §2.4's own established DELETE-has-no-idempotency precedent), never on `set-default`. Same TTL/replay/conflict/auth-before-idempotency semantics as §2.4, unchanged.
- **Mass-assignment protection**: same discipline as §2.4 — `id`/`organizationId`/`organization_id`/`deletedAt`/`createdAt`/`updatedAt` have no extraction path on any of these routes. `deals` additionally has no extraction path for `status` under any key. `pipelines/{id}/stages` additionally has no extraction path for a body-supplied `pipelineId` (always taken from the URL).

### 2.6 `/api/v1/activities`, `/api/v1/notes`, `/api/v1/tags`, `/api/v1/taggings` — implemented contract (M2.3D)

Session auth only, structured `{ "error": { "code", "message", "request_id" } }` envelope (§1), cursor pagination, `isSameOrigin()` CSRF check — same conventions as §2.4/§2.5, not repeated in full here. Domain logic lives entirely in `packages/crm` (M2.3B); every route here is a thin `route.ts` + `handlers.ts` pair.

- **Tenant/RBAC resolution**: identical chain to §2.4/§2.5. `activities:read/create/update/delete`, `notes:read/create/update/delete`, `tags:read/create/update/delete` (M2.3C, `08-Security.md` §3.1). **Taggings has no permission keys of its own** — every Taggings route checks the owning Tag's own `tags:*` key (`GET`→`tags:read`, `POST`→`tags:create`, `DELETE`→`tags:delete`), the same pattern `pipeline_stages` already established for `pipelines:*` (§2.5). `taggings/handlers.ts` imports `resolveActor` directly from `tags/handlers.ts` rather than duplicating it.
- **`GET /api/v1/activities`** — `{ activities: [...], nextCursor }`. Filters: `relatedToType`, `relatedToId`, `type`, `createdBy`, `completed` (`"true"`/`"false"`). A malformed `cursor`/`limit`/`relatedToType`/`type`/`completed`, or a malformed (non-UUID-shaped) `relatedToId`/`createdBy` → `400`.
- **`POST /api/v1/activities`** — body: `type` (required, one of `call`/`email`/`meeting`/`note`/`task`), `relatedToType` (required, one of `company`/`contact`/`deal`), `relatedToId` (required — despite the column being DB-nullable for the GDPR erasure path, M2.3A/M2.3B), `subject`, `body`, `dueAt`, `completedAt` (all optional). **`createdBy` is never a body field at all** — always the resolved actor's own `userId` (`packages/crm`'s `createActivity`, M2.3B); a client-supplied `createdBy` has no extraction path. `201` with `{ activity }`.
- **`GET /api/v1/activities/{id}`** / **`PATCH /api/v1/activities/{id}`** / **`DELETE /api/v1/activities/{id}`** — same cross-org/nonexistent-indistinguishable `404` rule as §2.4/§2.5, now also covering a malformed (non-UUID-shaped) `{id}` — indistinguishable from both. `PATCH` accepts `type`, `subject`, `body`, `dueAt`, `completedAt` only — **`relatedToType`/`relatedToId` have no extraction path at all** (not reassignable in Milestone 2.3, frozen design); a smuggled value in the body has no effect. `DELETE` is `packages/crm`'s `softDeleteActivity` only — never a physical `DELETE`.
- **`GET /api/v1/notes`** — `{ notes: [...], nextCursor }`. Filters: `relatedToType`, `relatedToId`. Same malformed-input `400` rules as Activities.
- **`POST /api/v1/notes`** — body: `relatedToType` (required), `relatedToId` (required, same GDPR-nullability caveat as Activities), `body` (required — non-whitespace, `packages/crm`'s own rule, despite the column also being DB-nullable for the GDPR erasure path). `201` with `{ note }`.
- **`GET /api/v1/notes/{id}`** / **`PATCH /api/v1/notes/{id}`** / **`DELETE /api/v1/notes/{id}`** — same rules as Activities' item routes. `PATCH` accepts `body` only.
- **`GET /api/v1/tags`** — `{ tags: [...], nextCursor }`. Cursor/limit only — no `name` filter, no full-text search (frozen 2.3 minimal filter scope; `packages/crm`'s `listTags` supports none either).
- **`POST /api/v1/tags`** — body: `name` (required, non-whitespace), `color` (optional, deliberately unvalidated free-form text — no design-token/hex-color system exists in this project's CRM tagging). `201` with `{ tag }`. Duplicate active name (case-insensitive, per organization) → `409` (`DuplicateTagNameError`).
- **`GET /api/v1/tags/{id}`** / **`PATCH /api/v1/tags/{id}`** / **`DELETE /api/v1/tags/{id}`** — same `404` rule. `PATCH` accepts `name`/`color`; a rename colliding with another active tag's name → `409`. `DELETE` (`softDeleteTag`) is a soft-delete only — existing Taggings referencing the tag are left untouched (they simply become unavailable as a target for *new* Taggings).
- **`GET /api/v1/taggings`** — `{ taggings: [...], nextCursor }`. Filters: `tagId`, `taggableType`, `taggableId`. Malformed `tagId`/`taggableId` (non-UUID) or invalid `taggableType` → `400`.
- **`POST /api/v1/taggings`** — body: `tagId` (required), `taggableType` (required, one of `company`/`contact`/`deal`), `taggableId` (required). Validates BOTH sides before insert — the tag itself (exists, active, same organization → `InvalidTagRelationshipError` → `400`) and the polymorphic target (same three checks per type → the matching `InvalidXRelationshipError` → `400`). Duplicate `(tag, target)` pair → `409` (`DuplicateTaggingError`). **No `Idempotency-Key` support at all** (deliberate, frozen 2.3 design) — the database's own `taggings_tag_id_taggable_type_taggable_id_key` unique constraint already makes a duplicate-submission race resolve to `409` without needing replay machinery. `201` with `{ tagging }`.
- **`DELETE /api/v1/taggings/{id}`** — **the one deliberate physical `DELETE` in this entire API** (frozen 2.3 design, mirrors the `taggings` table's own lack of a `deleted_at` column) — `packages/crm`'s `deleteTagging`, never a soft-delete. Same cross-org/nonexistent/malformed-`{id}`-indistinguishable `404` rule. **No `GET /api/v1/taggings/{id}` and no `PATCH /api/v1/taggings/{id}` exist at all** — a single Tagging is only ever reached through the collection's own filters, and a Tagging is never modified in place, only created or removed.
- **Malformed-UUID hardening (M2.3D, path `{id}` gap on pre-2.3D resources closed by Milestone 2.5C)**: before M2.3D, no route anywhere in this API — including §2.4/§2.5's Companies/Contacts/Deals/Pipelines — validated UUID *shape*; a malformed-but-non-empty string reached Postgres unvalidated and surfaced as a raw `invalid input syntax for type uuid` error (on some verbs, an entirely uncaught exception, confirmed by direct empirical testing during the 2.5C audit). `apps/web/app/api/v1/_shared/uuid.ts` (`isValidUuid`, reusing `packages/crm/src/pagination.ts`'s own regex) is the shared check every route in this API now uses to reject this before it ever reaches a query. A malformed path `{id}` (or, for nested pipeline-stage routes, either `{id}` or `{stageId}` independently) → `404` (extends the existing cross-org/nonexistent-indistinguishable doctrine to a third case); a malformed relationship/filter UUID (`relatedToId`, `tagId`, `taggableId`, `createdBy`) → `400` (matches how a well-formed-but-invalid relationship value already maps to `400`). **Milestone 2.5C scope note**: only path `{id}`/`{stageId}` parameters were retrofitted on Companies/Contacts/Deals/Pipelines/Pipeline Stages, and that gap is now fully closed for all of them. Malformed *query/body/filter* UUID fields on those same resources (e.g. `ownerId`, `companyId` filters) remain a separate, still-open gap — a malformed value in one of those fields still reaches Postgres unvalidated and surfaces as a generic `500` — deliberately out of 2.5C's scope.
- **GDPR historical reads**: `GET`/list on Activities and Notes correctly serialize a row produced by `execute_contact_erasure()` (M2.3A) — `relatedToId`/free-text columns `null`, `relatedToType` still `'contact'` — as an ordinary `200`, never a validation error or `500`, and never fabricates a replacement identifier or placeholder text.
- **Errors**: `ValidationError`, `InvalidCompanyRelationshipError`, `InvalidContactRelationshipError`, `InvalidDealRelationshipError` → `400` on Activities/Notes (`relatedToId` is a body field there) and on Taggings (`taggableId` is a body field there too). `InvalidTagRelationshipError` → `400` on Taggings (`tagId` is also a body field, never a path resource). `DuplicateTagNameError` → `409` on Tags. `DuplicateTaggingError` → `409` on Taggings. Anything unexpected → `500`, never a raw Postgres error/SQLSTATE/stack trace.
- **Idempotency**: `Idempotency-Key` wired on `POST`/`PATCH` for Activities, Notes, and Tags — never on `DELETE` (matching §2.4/§2.5's own precedent), never on any Taggings route (see above). Same TTL/replay/conflict/auth-before-idempotency semantics as §2.4/§2.5, unchanged.
- **Mass-assignment protection**: same discipline as §2.4/§2.5 — `id`/`organizationId`/`organization_id`/`createdBy`/`created_by`/`deletedAt`/`createdAt`/`updatedAt` have no extraction path on any of these routes. Activities/Notes `PATCH` additionally has no extraction path for `relatedToType`/`relatedToId`. Taggings has no `PATCH` route at all.

## 3. Authentication

Three distinct authentication paths:

1. **First-party session auth (product UI)**: Supabase Auth JWT, issued on login, carrying the user's identity. The *active organization* the request should be resolved against is determined per-request by the API middleware (`03-Database-Architecture.md` §5) — not baked into the JWT as a static claim — specifically so that an agency user switching between client organizations takes effect immediately, without a token reissue.
2. **API key auth (external integrations, and n8n)**: scoped keys (`arev_live_...` / `arev_test_...` prefix for environment clarity), passed as `Authorization: Bearer <key>`, backed by the `api_keys` table (`03-Database-Architecture.md` §2.1). Keys are hashed at rest, scoped to a single organization, and revocable individually via `/api/v1/api-keys`. **n8n uses this same mechanism** — every workflow is issued an `api_keys` row scoped to a `service` role/flag distinguishing it from a customer-issued key for monitoring/audit purposes, rather than a separate, undocumented credential type. This is a deliberate simplification: one credential primitive, one issuance/revocation path, one place RLS's tenant-context resolution has to reason about.
3. **Portal auth (customer portal)**: a **separate, magic-link-based flow** issuing a JWT scoped only to `portal_users` permissions. Enforcement is structural, not just a permission check: portal JWTs are only accepted by the `/api/v1/portal/*` route tree (§2); every other route rejects a portal-scoped token at the authentication layer before any authorization check even runs, so there is no code path where a portal session reaches an internal CRM/agent endpoint by a missed permission check.

## 4. Authorization

- Every request resolves to `(user_or_key, organization_id, role)` before touching a resource handler.
- Authorization is enforced at two layers: application-layer `can(actor, action, resource)` checks (see `02-Software-Architecture.md` §7, RBAC facade) as the primary gate, with Postgres RLS as defense-in-depth beneath it.
- Agency-level endpoints (`/api/v1/organizations` list, roll-up reads) require `agency_owner`/`agency_admin` and route through the explicit roll-up views — never a general bypass flag.
- API keys carry their own scoped permission set (e.g., a key can be issued read-only, or scoped to only `contacts` + `deals`) independent of the issuing user's own role, so an agency can hand a narrow key to a client's tool without over-granting.
- Portal-reachable resources are a separate route tree (`/api/v1/portal/*`, §2), not a permission flag layered onto the staff API — this is a structural choice, not just a policy one, precisely so "is this endpoint portal-safe" is answerable by looking at the URL, not by auditing every permission check.

## 5. API Versioning

- URL-path versioning (`/api/v1/...`) — chosen over header-based versioning for discoverability and simpler debugging/curl-ability for external integrators.
- A version is supported for a minimum of 12 months after the next version ships; deprecation is announced via a `Deprecation` and `Sunset` response header before removal, never a silent break.
- Additive changes (new optional fields, new endpoints) do not bump the version. Breaking changes (removed fields, changed semantics, changed auth) require a new version.

## 6. Rate Limiting

- Enforced per tenant (`organization_id` or API key), not globally — one tenant's enrichment-heavy usage must never degrade another tenant's experience.
- Default tier (**directional, to be set from real load-testing, not treated as validated**): on the order of several hundred requests/minute per organization for read endpoints, an order of magnitude lower for write/mutation endpoints, configurable per plan.
- The public tracking endpoints (§2) are rate-limited per `anonymous_id`/source IP/resolved tracking site — three independent dimensions, not per tenant — and separately from the rest of this section: their traffic profile (public, spiky, potentially abusive) has nothing in common with authenticated tenant API calls.
- Webhook receivers are rate-limited per source provider signature, not per tenant, since inbound webhook volume is provider-driven.
- `429` responses carry `Retry-After` and `X-RateLimit-Remaining` headers; clients are expected to back off, not retry immediately.
- Agent-triggered API calls (an agent calling internal tools, which route through this same API) are subject to a separate, stricter budget to contain runaway agent loops from a prompt/tool-call bug (`05-AI-Agent-Architecture.md` §7).

## 7. Webhooks

**Inbound** (`/api/v1/webhooks/*`):
- Every inbound webhook is signature-verified against the provider's signing secret before processing (HMAC comparison, constant-time).
- Processing is idempotent — a dedupe table keyed on `(provider, provider_event_id)` (`webhook_events_seen`, `03-Database-Architecture.md` §2.10) prevents double-processing of retried deliveries.
- **Providers call these endpoints directly** — a bounce/open notification, a LinkedIn task result, an enrichment completion all land on `/api/v1/webhooks/*` from the provider itself, not via n8n. n8n is never a webhook target for third-party providers; the app's job is to verify, dedupe, persist the result, and emit an internal domain event, which n8n then reacts to like any other event-driven workflow (see `02-Software-Architecture.md` §5, `06-n8n-Workflow-Architecture.md` §14).

**Outbound** (tenant-configurable, managed via `/api/v1/webhook-subscriptions`, §2):
- Agencies/organizations register their own webhook endpoints (backed by the `webhook_subscriptions` table, `03-Database-Architecture.md` §2.10) to receive domain events (`deal.stage_changed`, `proposal.accepted`, `lead_score.recalculated`).
- Delivery is signed (HMAC with the per-subscription `signing_secret_encrypted`) so receivers can verify authenticity.
- Retried with exponential backoff on failure; a webhook endpoint failing repeatedly is auto-disabled (`disabled_at` set) and surfaced to the tenant admin, not retried indefinitely.

**Ordinary mutations, not just webhooks**: the `Idempotency-Key` support stated in §1 applies to every `POST`/`PATCH` on the authenticated API, not only to webhook delivery — a duplicate `POST /api/v1/deals` from a client-side retry is exactly as much a correctness risk as a duplicate webhook delivery, and is protected the same way.

## 8. Integration Architecture

- The REST API and the webhook layer together are the **only** way external systems — including n8n itself — touch tenant data. n8n does not have direct Postgres access; it calls the same authenticated API surface a third-party integrator would, using an `api_keys` row scoped to a `service` role (§3) issued per workflow, resolved through the same request-scoped tenant-context mechanism as any other caller (`03-Database-Architecture.md` §5).
- This symmetry (n8n as "just another API consumer," using the same credential primitive as anyone else) is what keeps the provider-agnostic promise real: replacing n8n itself with a different automation engine in the future would not require redesigning the data access layer, the credential model, or the authorization path.
- Third-party integrations an agency wants to build (e.g., syncing to their own BI tool) use the same scoped API keys described in §3, issued via `/api/v1/api-keys` — there is no "internal-only" API surface with weaker auth than what's offered externally.
